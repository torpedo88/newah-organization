<objective>
## Goal

Turn an empty repository into a typed Next.js 16 App Router application, styled with Tailwind and shadcn/ui, wired to a hosted Supabase project through browser and server clients, and deployed successfully to Vercel.

## Purpose

Every later phase — org pages, event list, registration portal — builds on this scaffold. Getting the deploy pipeline and Supabase wiring correct once, up front, means Phase 2 onward is feature work rather than infrastructure debugging. It also proves the stack decision (Vercel + Supabase) end to end before any real content depends on it.

## Output

- A running Next.js app with a placeholder home page
- Tailwind + shadcn/ui configured, one shadcn component installed as proof
- `lib/supabase/client.ts` and `lib/supabase/server.ts` exporting typed clients
- `lib/env.ts` validating required public environment variables at startup
- `.env.example` documenting every variable without any real values
- <!-- audit-added --> A pinned toolchain (`.nvmrc`, `engines.node`, committed lockfile) for reproducible builds
- <!-- audit-added --> A CI workflow gating lint, typecheck, build, and secret scanning on every pull request
- A live Vercel deployment URL, not indexable until launch
</objective>

<task type="auto">
  <name>Task 2: Wire typed Supabase clients with validated environment variables</name>
  <files>lib/supabase/client.ts, lib/supabase/server.ts, lib/env.ts, .env.example, package.json</files>
  <action>
    Install `@supabase/supabase-js`, `@supabase/ssr`, and <!-- audit-added --> `server-only`. The `server-only` package must actually be installed — `import 'server-only'` is an inert string without it and provides no protection.

    Create lib/env.ts exporting a validated environment object for the two public variables only: NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY. Throw a named, descriptive error naming the specific missing variable when either is absent or empty, so misconfiguration fails at startup rather than at first query. Do not fall back to defaults, placeholders, or an unauthenticated client.

    <!-- audit-added --> lib/env.ts must NOT read or validate SUPABASE_SERVICE_ROLE_KEY. Non-public variables are `undefined` in the browser bundle, so validating a server-only variable inside a module that client code imports would throw at runtime in every visitor's browser. This plan creates no service-role client at all, so the variable has no reader and belongs in no module yet. Phase 5 introduces it deliberately in a server-only module with its own validation.

    <!-- audit-added --> Correspondingly, .env.example lists only NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY, each with an empty value and a one-line comment. Documenting a service-role slot invites someone to fill it in before anything is ready to guard it.

    Create lib/supabase/client.ts exporting a browser client built with createBrowserClient from @supabase/ssr, using only the two NEXT_PUBLIC_ variables.
    Create lib/supabase/server.ts exporting a server client built with createServerClient from @supabase/ssr, using Next.js cookies() for session handling. Put `import 'server-only'` at the top so a client component importing it fails at build time rather than leaking server code to the browser.

    Security requirements — these are not stylistic:
    - SUPABASE_SERVICE_ROLE_KEY must never be prefixed with NEXT_PUBLIC_ and must never be read from lib/supabase/client.ts or lib/env.ts. That key bypasses Row Level Security; exposing it in a client bundle would give any visitor full read and write access to member and attendee data.
    - Do not create a service-role client in this plan at all. Nothing needs it yet, and an unused privileged client is a standing risk.
    - Do not write real keys into .env.example, README.md, or any committed file.

    Avoid: the deprecated @supabase/auth-helpers-nextjs package; instantiating clients at module scope in server code in a way that shares state across requests.
  </action>
  <verify>`pnpm build` exits 0; `grep -rn "SERVICE_ROLE" lib/ app/` returns no matches; `node -p "require('./package.json').dependencies['server-only']"` prints a version; temporarily unsetting NEXT_PUBLIC_SUPABASE_URL makes `pnpm build` fail with an error naming that variable</verify>
  <done>AC-2 and AC-7 satisfied: typed separated clients, fail-fast named env validation, no server-only variable reachable from client code</done>
</task>

A production Vercel deploy is publicly crawlable, and a half-built page indexed under this organization's name is a reputational cost that is hard to reverse.

<task type="auto">
  <!-- audit-added: entire task -->
  <name>Task 4: Prove the committed tree is clean of secrets</name>
  <files>(no files modified — verification only)</files>
  <action>
    Scan the committed tree rather than the working directory. The working directory contains .next build output and node_modules, which produce false positives and are not what leaks; what leaks is what is committed and pushed.

    Run, from the repository root:
    `git ls-files -z | xargs -0 grep -nIiE "eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}|sb_secret_[A-Za-z0-9]{8,}|sb_publishable_[A-Za-z0-9]{8,}|(service_role|anon)[\"']?[[:space:]]*[:=][[:space:]]*[\"']?eyJ|postgres(ql)?://[^[:space:]]*:[^[:space:]]*@" || echo "CLEAN"`

    <!-- apply-corrected --> The pattern matches real credential shapes rather than loose substrings. An earlier draft matched any `eyJ` followed by base64 characters, which fired on `pnpm-lock.yaml` integrity hashes, and matched the bare word `service_role`, which fired on planning documents that merely discuss the prohibition. Paths are deliberately NOT excluded — a key pasted into a `.paul/` planning note must still be caught.

    After running the scan, prove the detector is alive rather than trusting a CLEAN result: grep a planted three-segment JWT string from a temp file outside the repo and confirm it matches. A scan that cannot fail is not evidence.

    Then confirm the ignore rules actually hold:
    `git ls-files | grep -E "^\.env|^\.vercel" || echo "NO ENV OR VERCEL FILES TRACKED"`

    If any match is found, stop. Do not proceed to deploy, and do not simply delete the file in a new commit — a secret that reached a commit is in the history and the corresponding key must be rotated in the Supabase dashboard before anything else happens.
  </action>
  <verify>The first command prints CLEAN; the second prints NO ENV OR VERCEL FILES TRACKED</verify>
  <done>AC-3 satisfied: the committed tree is demonstrably free of credentials</done>
</task>
