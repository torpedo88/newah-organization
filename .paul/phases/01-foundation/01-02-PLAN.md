<objective>
## Goal

Create the `people`, `events`, and `registrations` tables as committed SQL migrations, enable Row Level Security with deny-by-default, add exactly the policies the public site needs, and prove empirically — with the real anon key against the real database — that an anonymous client can read published events and cannot read a single row of `people` or `registrations`.

## Purpose

This plan, not the scaffold, is what protects the community. The Supabase anon key ships in the browser bundle and is readable by anyone who opens devtools; it is public by design. RLS is therefore not a layer of defense, it is the only one. A wrong policy here publishes the names, emails, and phone numbers of people who trusted a cultural organization with them, and nobody would find out until someone told them.

The verification in this plan is deliberately empirical rather than by inspection. Reading a policy and believing it is correct is how RLS mistakes ship.

## Output

- `supabase/migrations/0001_initial_schema.sql` — tables, constraints, indexes
- `supabase/migrations/0002_row_level_security.sql` — RLS enabled and policies
- `lib/database.types.ts` — generated TypeScript types
- `supabase/README.md` — how to apply migrations and re-run the policy proof
- A recorded transcript of the anon-key probe showing what was and was not readable
</objective>

<task type="auto">
  <name>Task 1: Write the initial schema migration</name>
  <files>supabase/migrations/0001_initial_schema.sql, supabase/README.md</files>
  <action>
    Create `supabase/migrations/0001_initial_schema.sql`. Migrations are committed SQL files applied in filename order — the project has no local Supabase Docker environment, so these files are the only record of schema truth. A change made in the dashboard and not written here does not exist.

    Enable the `citext` extension, then create:

    **people** — the identity spine. `id uuid primary key default gen_random_uuid()`, `email citext not null unique`, `full_name text not null`, `phone text`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()`.
    <!-- audit-added --> Add column-level checks so malformed rows fail at the database rather than relying on application validation that a future Server Action might skip: `email` must match a basic address shape and be at most 254 characters; `full_name` must be between 1 and 200 characters after trimming. The `anon` INSERT policy is deliberately permissive, so these constraints are the only thing bounding what an unauthenticated writer can store.

    Use `citext` for email rather than `text`, because "Person@Example.com" and "person@example.com" are the same human and a case-sensitive unique index would create two rows for them — which is precisely the duplicate-identity problem the spine exists to prevent.

    **events** — `id uuid primary key default gen_random_uuid()`, `slug text not null unique`, `title text not null`, `description text`, `starts_at timestamptz not null`, `ends_at timestamptz`, `location text`, `capacity integer check (capacity is null or capacity > 0)`, `cover_image_path text`, `status text not null default 'draft' check (status in ('draft','published'))`, `created_at timestamptz not null default now()`.
    `capacity` null means unlimited. `status` is a checked text column rather than an enum so adding a state later is a migration, not a type surgery.

    **registrations** — `id uuid primary key default gen_random_uuid()`, `event_id uuid not null references events(id) on delete cascade`, `person_id uuid not null references people(id) on delete cascade`, `party_size integer not null default 1 check (party_size between 1 and 20)`, `notes text`, `status text not null default 'confirmed' check (status in ('confirmed','cancelled'))`, `created_at timestamptz not null default now()`, and `unique (event_id, person_id)`.
    The unique constraint is what makes a double-submitted form harmless: the second insert is a conflict to swallow, not a duplicate attendee to clean up later.

    Add indexes: `events(status, starts_at)` for the public list query, `registrations(event_id)` for per-event lookups.

    Add an `updated_at` trigger for `people`.

    Write `supabase/README.md` documenting how to apply migrations against the hosted project, that the dashboard is never the source of truth, and how to re-run the policy proof from Task 3.

    Avoid: `text` for email; a Postgres enum for `status`; `on delete set null` on either foreign key — an orphaned registration pointing at nothing is worse than no row; storing full image binaries in Postgres rather than a Storage path.
  </action>
  <verify>Apply `0001` to the project and confirm `\d people`, `\d events`, `\d registrations` show the constraints and indexes; insert two people differing only in email case and confirm the second is rejected by the unique index</verify>
  <done>AC-1 and AC-2 satisfied: schema is replayable from committed SQL and identity is case-insensitive and unique</done>
</task>

<task type="auto">
  <name>Task 2: Write the RLS migration — deny by default, then grant exactly what the public site needs</name>
  <files>supabase/migrations/0002_row_level_security.sql</files>
  <action>
    Invoke `/engineering-skills:senior-security` before writing this file.

    Create `supabase/migrations/0002_row_level_security.sql`.

    Enable RLS on all three tables first. In Postgres, enabling RLS with no policy denies everything — that is the desired starting point. Add only these policies:

    | Table | Role | Operation | Condition |
    |-------|------|-----------|-----------|
    | `events` | `anon` | SELECT | `status = 'published'` |
    | `people` | `anon` | INSERT | `with check (true)` |
    | `registrations` | `anon` | INSERT | <!-- audit-added --> `with check (exists (select 1 from events e where e.id = event_id and e.status = 'published'))` |

    <!-- audit-added --> The `registrations` check is not boilerplate. An unconditional `with check (true)` would let anyone holding the public anon key insert registrations against **draft** events — events the board has not announced, possibly not finalized, and cannot see filling with junk rows. The subquery is evaluated with the inserting role's own RLS, so it sees exactly the published events `anon` is allowed to see, which is the behavior we want. Without this, "draft means invisible" holds for reads and silently fails for writes.

    Write **no SELECT policy** for `people` and **no SELECT policy** for `registrations`. This asymmetry is the entire point of the plan: the anon key is public, so a SELECT policy on either table is equivalent to publishing the attendee list. An INSERT policy without a SELECT policy lets the registration form write while leaving the data unreadable to the same credential.

    Because `people` has an INSERT policy but no SELECT policy, an `on conflict ... do update ... returning` upsert will fail to return the row. Do not solve this by adding a SELECT policy. Plan 04 (Registration) resolves it with a `security definer` function that performs the upsert server-side and returns only the id — noted here so the next implementer does not reach for the dangerous fix under time pressure.

    Grant no policies to `authenticated` yet. Board access arrives in Phase 5 together with the `profiles` table and role model. Until then `authenticated` inherits deny-by-default, which is correct: nobody needs board access before the admin surface exists, and a placeholder policy written now would be a guess about a role model that does not exist.

    Add a SQL comment above each policy stating what it permits and why, so a future reader does not "clean up" the missing SELECT policies as an oversight.

    <!-- audit-added --> Document a revert path at the bottom of the migration as a SQL comment: the exact `drop policy` statements that undo this file. A wrong RLS policy is a live data-exposure incident, and the response to one is measured in minutes — nobody should be composing revert SQL from memory while community data is readable.

    Avoid: `using (true)` on any SELECT policy; policies on `public` rather than a named role; disabling RLS "temporarily" to debug — use the service role in a server-only context instead, and not in this plan, which creates no service-role client.
  </action>
  <verify>Apply `0002`; query `pg_policies` and confirm exactly three policies exist with the expected roles and commands, and that no SELECT policy exists on `people` or `registrations`; confirm `rowsecurity` is true for all three tables in `pg_tables`</verify>
  <done>AC-3 satisfied: RLS enabled everywhere, deny-by-default, exactly three policies</done>
</task>

<task type="auto">
  <name>Task 3: Prove the policies empirically with the real anon key</name>
  <files>(no files modified — verification, transcript recorded in the SUMMARY)</files>
  <action>
    Invoke `/engineering-skills:senior-security` again before this task, and approach it as an attacker rather than as the author. The goal is to make the policies fail; if you cannot, they hold.

    <!-- audit-added --> Run the probes from a small Node script using `@supabase/supabase-js`, reading `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from `.env.local`. Keep the script under `scripts/` and never inline a key into it. Do not probe through the application UI — that tests the UI, not the policy, and the UI does not exist yet.

    Seed fixture rows via the Supabase SQL editor or a service-role-free admin session — **not** through the anon client, which by design cannot create a draft event. One `published` event, one `draft` event, one person, one registration for that person.

    Then, using a client constructed with the **anon key only** — the same key the browser gets, never the service role — execute and record the actual result of each probe:

    1. `select * from events` → expect exactly the published event; the draft must be absent
    2. `select * from events where status = 'draft'` → expect zero rows, proving the filter is enforced by policy rather than by the query
    3. `select * from people` → expect **zero rows**
    4. `select * from registrations` → expect **zero rows**
    5. `select count(*) from people` → expect 0, confirming aggregates do not leak existence
    6. Insert a new person → expect success
    7. Insert a registration for the published event → expect success
    8. Immediately `select` the row just inserted in step 7 → expect **zero rows**
    9. Insert the same (event_id, person_id) again → expect a unique-violation error, not a second row
    10. Attempt to select `people` joined to `registrations` → expect zero rows, confirming no leak via join
    <!-- audit-added -->
    11. Attempt to `update` the published event's title → expect denial. No UPDATE policy exists, so deny-by-default should refuse it; an anon UPDATE on `events` would let a stranger rewrite event details on the public site.
    12. Attempt to `delete` the published event → expect denial
    13. Attempt to `update` and `delete` the registration inserted in step 7 → expect denial both times
    14. Attempt to insert a registration whose `event_id` is the **draft** event → expect denial, proving the published-only check on the INSERT policy

    Probes 11 through 14 exist because deny-by-default is an assumption until something tests it. A policy set can look correct and still permit writes nobody intended.

    Any probe returning private rows is a stop-the-line failure. Do not adjust the probe to produce a passing result; fix the policy and re-run every probe from the start.

    Record the full transcript in the SUMMARY. Probes 3, 4, 5, 8, and 10 are the ones that matter — they are the difference between a community trusting this organization with its contact details and not.

    Avoid: running probes with the service role key, which bypasses RLS and would make every check pass meaninglessly; testing through the application UI instead of directly against the database, which tests the UI rather than the policy.
  </action>
  <verify>All ten probes produce their expected result, executed against the real project with the anon key, with the transcript captured</verify>
  <done>AC-4, AC-5 and AC-6 satisfied: anonymous access is empirically confined to published events plus blind inserts</done>
</task>
