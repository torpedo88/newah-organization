**1. P1 — Form validation silently fails.**

Source: [package.json](../package.json), [registration-form.tsx](../components/registration/registration-form.tsx).

Open `/register` and click **Complete Registration** without filling anything in. Chrome raises an unhandled `ZodError`; no field messages appear. The same failure occurs when food is selected without a description or an adult guest has a name but no contact details. Choosing a donation preset while other fields are incomplete also raises errors.

The lockfile installs `@hookform/resolvers` 3.10.0 with Zod 4.6.5. The installed resolver checks `error.errors`, whereas this Zod version supplies `error.issues`, so validation exceptions escape instead of populating React Hook Form's errors. A direct invocation of the installed resolver reproduced the same failure.

Fix target: align the resolver with the installed Zod version, then assert visible errors and absence of unhandled browser exceptions for all invalid paths.

**2. P1 — Every normal registration insert requests a read forbidden by RLS.**

Source: [register.ts](../lib/actions/register.ts), line 66; [0003](../supabase/migrations/0003_fix_registrations_rls.sql).

The server action uses the anonymous Supabase client and calls `.insert(row).select("id").single()`. Migration 0003 intentionally removes anonymous SELECT access. PostgreSQL rejects an INSERT with `RETURNING id` under this policy with `42501: new row violates row-level security policy for table "registrations"`.

Verified directly against PostgreSQL, including a row with a valid legacy registration type to isolate this from finding 3. The same insert without `RETURNING` succeeds. Also submitted a valid form through the real Next.js Server Action to a local HTTP adapter backed by that database: the user sees the RLS error and registration fails.

Fix target: use a carefully scoped server write or database function that returns the required identifier without making attendee rows publicly readable. The fallback insert has the same forbidden read.

**3. P1 — The application and migrated schema disagree about registration type.**

Source: [register.ts](../lib/actions/register.ts), line 110; [base schema](../lib/supabase/migrations.sql), line 5; [0005](../supabase/migrations/0005_jatra_with_cause.sql); [consolidated migrations](../APPLY-MIGRATIONS.sql).

The action writes `registration_type: "event"`, but the original CHECK constraint allows only `food` and `donation`. Neither the ordered migrations nor the consolidated script removes or changes that constraint. With the RLS RETURNING issue removed from the probe, an `event` insert fails with `23514: registrations_registration_type_check`.

Fix target: add a migration matching the new registration model. Merely making the column nullable does not change its allowed non-null values.

**4. P1 — Anonymous callers can insert donations marked paid.**

Source: [0003](../supabase/migrations/0003_fix_registrations_rls.sql), line 31; [0005](../supabase/migrations/0005_jatra_with_cause.sql); [admin page](../app/admin/page.tsx).

`WITH CHECK (true)` permits anonymous INSERTs containing `payment_status = 'paid'`, arbitrary donation/net amounts, and asserted consent. A local anonymous insert using a valid legacy type, $10,000 in donation/net fields, and `paid` succeeded. The admin totals trust these fields, so the policy does not enforce the stated rule that only Stripe can establish payment.

Fix target: enforce initial payment/consent rules at the actual write boundary and prevent public callers from setting trusted payment fields. Client validation and webhook signature checks alone do not constrain direct database API inserts. Anonymous SELECT access remained closed in the probes.

**5. P1 — Stripe session linkage cannot be saved; unmatched webhooks are acknowledged.**

Source: [register.ts](../lib/actions/register.ts), line 223; [webhook](../app/api/stripe/webhook/route.ts), line 55.

Checkout tries to update `stripe_session_id` through the anonymous client, but the schema grants that role no UPDATE policy. An equivalent anonymous update affected zero rows. The action ignores the update result. The webhook later finds registrations solely by this missing session ID.

A correctly signed local webhook for an unknown session received HTTP 200 `{ "received": true }` while the seeded registration stayed pending. Zero matched rows are treated as successful processing. This issue remains after the registration insert blockers are fixed.

Fix target: persist checkout linkage through an authorized server path, check that the update succeeded, and handle an unmatched payment explicitly so it is not silently lost.

**6. P2 — Checkout return URLs discard confirmation and cancellation state.**

Source: [register.ts](../lib/actions/register.ts), line 219; [register page](../app/register/page.tsx).

Visit `/register?donation=success&code=NOA-TEST`, then `/register?donation=cancelled&code=NOA-TEST`. Both display a blank registration form; neither displays the registration code or explains what happened. The page ignores the query parameters created by checkout. This invites a donor to register again.

Fix target: show a return state tied to the existing registration and server-verified payment information. A success query string must not itself establish payment.

**7. P2 — The board cannot see additional adults' names or contact details.**

Source: [admin page](../app/admin/page.tsx), registration query and table.

Seed a registration with one additional named adult, then sign in. The primary registrant and guest count appear, but the guest's name, email, and phone do not. `adult_guests` is absent from both the SELECT list and rendered table. This prevents the board from preparing the additional name tags promised by the form without using the database dashboard.

Fix target: make the collected adult details available in the authorized board view or export.

**8. P2 — Donation bounds can be bypassed with a contradictory choice.**

Source: [registration validation](../lib/validation/registration.ts), line 83; [register.ts](../lib/actions/register.ts), line 98.

Submit otherwise valid input with `donationChoice: "none"` and `donationAmount: 20000`. The schema accepts it because amount bounds run only for the `amount` choice. The action derives the charge from `donationAmount` without checking the choice. Once registration succeeds, this path can attempt an amount above the advertised maximum despite the explicit decline. The normal UI clears the amount when declining; the server boundary still needs to enforce the relationship.

Fix target: make choice and amount consistent on the server, and derive payment only from a validated donation choice. Fractional-cent input such as `1.001` is also accepted and silently rounded.

**Additional findings with narrower scope**

- The webhook maps every `checkout.session.completed` to paid without inspecting `payment_status`, ignores `checkout.session.async_payment_succeeded`, and permits later events to overwrite paid with failed. Synthetic, locally signed events demonstrated unpaid → paid and paid → failed. These probes verify handler behavior, not that Stripe will emit every tested sequence for this checkout configuration. Reconcile the handler with the payment methods actually enabled.
- Migration 0003 claims to be safe to rerun but fails with `42710` because it recreates `anon_insert_registrations` without dropping it. The consolidated migration does drop it correctly.
- The success screen always says a confirmation email was sent, while the action can skip sending when Resend is unconfigured or swallow a provider error. This was identified from code; no email delivery test was performed.
- `.env.example` omits Stripe secret/webhook configuration and the explicit site URL override used by the code.
